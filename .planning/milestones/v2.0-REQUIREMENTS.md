# Requirements: OpenRund v2.0 Python OpenRund

**Defined:** 2026-08-04
**Core Value:** Provide a minimal but authoritative runtime where long-running agent runs remain durable, lawful, replayable, resumable, portable, and inspectable even when models, workers, or infrastructure fail.

## v2.0 Requirements

These requirements define a complete Python implementation. Compatibility applies to runtime semantics and serialized data; Python package and callable API design should be idiomatic rather than mechanically reproducing an earlier implementation structure.

### Semantic Compatibility

- [x] **SEM-01**: Python users can construct and validate the canonical `Run`, `Command`, `Event`, `Message`, `ModelCall`, `Action`, `Wait`, `Delegation`, `Check`, `Checkpoint`, `Annotation`, `Artifact`, `Capability`, `Authority`, `Lease`, `Bundle`, and `View` concepts with kind-safe identifiers and non-authoritative secondary-surface names.
- [x] **SEM-02**: Python users can decode, encode, round-trip, hash, and reject versioned canonical wire data deterministically, preserving Event names, envelope and payload keys, enum strings, missing-versus-null behavior, IDs, timestamps, causation/correlation links, and `.orun` commitments proven by frozen golden fixtures.

### Canonical History

- [x] **EVT-01**: Runtime hosts can append immutable Events per Run only at an expected position, receive a distinct conflict for stale positions, and read deterministic gap-free history whose committed success cannot be invalidated by a subscriber failure.

### Engine Authority

- [x] **ENG-01**: Every attempted mutation from a model, runtime API, timer, Capability result, operator, Delegation handoff, or recovery procedure enters one Engine-owned Command evaluation path before any state-changing Event is appended.
- [x] **ENG-02**: Operators can inspect a persisted `command.recorded` fact for every attempted mutation, including origin, operation, accepted/rejected/deferred/superseded decision, decision trace, result Event IDs, Wait linkage, and replacement linkage, with rejected or superseded Commands producing no target lifecycle Events.

### Run And Model Interaction

- [x] **RUN-01**: Runtime hosts can bootstrap, advance, complete, fail, and cancel Runs through lawful Commands, while terminal Runs reject later mutation and completion remains illegal until required Waits, Checks, Artifacts, joins, and unknown outcomes are satisfied.
- [x] **MSG-01**: Runtime hosts can persist and replay Message and ModelCall lifecycles, parse the supported Operation set as untrusted proposals, distinguish provider/transport/parse failures from rejected Commands, and prevent provider output from becoming authority.

### Capability And Action Semantics

- [x] **CAP-01**: Extension authors can register validated Capability definitions with action schemas, access modes, reliability, batching, cancellation, Artifact, and transport metadata, then execute through in-process or strict stdio JSON-RPC transports that return validated `CapabilityResult` data rather than Events.
- [x] **ACT-01**: Operators can observe an Engine-controlled Action lifecycle in which accepted mutating work is durably recorded before dispatch, worker results become compact output/effect/evidence metadata plus Artifact references, cancellation follows declared reliability, and each Action has exactly one current completed/failed/cancelled/unknown outcome.
- [x] **ACT-02**: Operators can record and replay an explicit unknown Action outcome, block completion through reconciliation semantics, and append evidence-backed `action.reconciled` facts without rewriting the original uncertainty or blindly retrying consequential effects.

### Waits And Approval

- [x] **WAIT-01**: Runtime hosts can create, replay, resolve, cancel, and expire approval, interaction, timer, join, and reconciliation Waits exactly once, with unresolved Waits deriving waiting state and blocking the relevant advancement.
- [x] **WAIT-02**: Operators can approve, deny, or cancel a valid deferred Action, optionally revise input within declared schemas and writable roots, and have the Engine revalidate current Authority, policy, resource scope, and revised input through a new Command before dispatch; illegal Operations never reach approval.

### Delegation And Governance

- [x] **DEL-01**: Runtime hosts can create bounded delegated Runs with explicit objectives, Authority, budgets, result schemas, nesting, cancellation, late-handoff, and all/any/quorum join contracts, with atomic or deterministically recoverable parent/child establishment and no automatic parent advancement from child terminal state.
- [x] **GOV-01**: Operators can grant and revoke durable Authority and inspect legality decisions that account for capability metadata, contracts, policy, resource/workspace scope, budgets, required Checks, outcome constraints, Delegation lineage, and tenant/security context without allowing approval or registration to override hard invariants.

### Checks And Recovery Boundaries

- [x] **CHK-01**: Runtime hosts can record and replay semantic and diagnostic Checks, Checkpoints, and Annotations with Artifact-backed evidence, use semantic Check requirements in completion contracts, and keep explanatory surfaces non-authoritative.

### Artifacts And Derived Views

- [x] **ART-01**: Runtime hosts can store immutable Artifact metadata and bytes with content integrity, reject conflicting reuse of an Artifact ID, stage blob/metadata writes with explicit crash recovery, record unavailable content, and keep large durable output out of Event payloads.
- [x] **VIEW-01**: Operators can deterministically rebuild Run status/readiness, timeline, Wait queues, Action status/receipts/reconciliation, Artifact index, Checkpoints, Delegation state, and Reports from complete Events and Artifacts at a known watermark without Views appending Events or independently deciding legality.

### Local Persistence And Execution Custody

- [x] **STO-01**: Runtime hosts can use real SQLite Event and Artifact stores whose migrations, expected-position transactions, duplicate-ID handling, ordered reads, restart/reopen behavior, bounded busy handling, and partial-failure recovery pass concurrency and crash-injection tests.
- [x] **STO-02**: Runtime hosts can coordinate executors with scoped acquire/release/expiry Lease semantics and place each Run's `runtime/`, `workspace/`, and `exports/` under deterministic configurable Run-home paths without treating a Lease as runtime Authority.

### Portable Bundles

- [x] **BND-01**: Operators can export, semantically verify, replay, atomically stage-import, and assess resumability of complete/audit/redacted `.orun` Bundles containing canonical Events, hash-chain and file commitments, available Artifacts, derived summaries, policy/capability/provider metadata, Reports, and explicit resume requirements.

### Built-In Capabilities

- [x] **BUILTIN-01**: Runtime hosts can govern workspace-bounded filesystem read/list/stat/write/update/delete/move/diff operations with read-only posture, traversal and symlink protection, stale-hash and overwrite checks, atomic mutation where possible, and effect/evidence/Artifact results.
- [x] **BUILTIN-02**: Runtime hosts can govern Markdown read, whole-document write, and structured patch operations covering hashes, diffs, headings/sections, ranges, append, and frontmatter through a root-bounded worker whose errors and results cross the generic Capability boundary.
- [x] **BUILTIN-03**: Runtime hosts can govern bounded process execution and local-only git status/diff/head/apply/stage/commit operations with constrained roots, arguments, environment, shell, timeout, cancellation, and Artifact-backed output while excluding network and credential operations.

### Providers

- [x] **PROV-01**: Runtime hosts can use OpenAI, Anthropic, and local OpenAI-compatible adapters that share provider-neutral Operation normalization, perform direct async HTTP/SSE calls, return proposals only, redact remote failure detail, fail safely on malformed output, support deterministic mock coverage, and provide opt-in real drift checks.

### Operator Surface And Demonstration

- [x] **CLI-01**: Operators can use the installed `openrund` command for create/run/inspect, timeline/replay, Wait and approval control, Command explanations, Action reconciliation and receipts, readiness, Checks, Artifacts, and every Bundle operation with deterministic human and JSON output, meaningful exit codes, and all legality delegated to the Engine.
- [x] **DEMO-01**: Users can run one deterministic installed-package governed coding demonstration that proves illegal mutation rejection before approval, approval deferral/resume, filesystem/process/git/documents execution, unknown outcome and reconciliation, delegated join, Check-gated completion, CLI explanations, and `.orun` export/verify/replay/import/resume assessment.

### Python-Native Developer Experience

- [x] **DX-01**: Python users can work with `snake_case` objects and explicit canonical wire aliases through a single codec boundary, without serialized dictionaries leaking through Engine code.
- [x] **DX-02**: Python users receive frozen typed domain values, precise unions, complete public annotations, and a shipped `py.typed` marker while untrusted boundaries still perform runtime validation.
- [x] **DX-03**: Runtime hosts can inject stores, clocks, ID factories, providers, transports, and reporters through small structural `Protocol` seams with deterministic in-memory implementations for contract tests.
- [x] **DX-04**: Python users can operate an async-first Engine whose runtime, storage, provider, and worker resources have explicit context-managed lifetimes and whose cancellation semantics preserve ModelCall and Action facts without orphan tasks or processes.
- [x] **DX-05**: Python callers can pass `os.PathLike` values for runtime homes, workspace roots, databases, Artifacts, and Bundles while boundary normalization preserves sandbox and wire-format rules.
- [x] **DX-06**: Users can install one standards-based `openrund` distribution from wheel or sdist, use a minimal base dependency set plus targeted extras, and invoke its console script without Node or repository-local tooling.
- [x] **DX-08**: Python callers receive a documented semantic exception hierarchy for validation, optimistic concurrency, storage integrity, transport, and Capability protocol failures while rejected/deferred/superseded legality remains a persisted decision result rather than an exception.
- [x] **DX-09**: Python users can create the first lawful local Run through an explicit assembly factory that wires SQLite, Run-home paths, built-in Capabilities, providers, operator input, and reporting while keeping every dependency injectable and granting no implicit Authority or writable root.
- [x] **DX-10**: Python users can rely on a deliberate top-level import surface for the Engine, local assembly, IDs, contracts, Views, Capability/provider factories, storage, and operator results, protected by import and CLI/library parity tests.

### Verification, Documentation, And Cutover

- [x] **REL-01**: Maintainers can verify v2.0 through pytest (including state-machine, concurrency, fault-injection, malicious-input, and end-to-end tests), strict typing, lint/hygiene, coverage, package-content, security audit, documentation/link, demo, clean-wheel/sdist, and opt-in live-provider checks across supported Python 3.12–3.14 releases.
- [x] **REL-02**: Users and contributors encounter only Python-native live source, tests, examples, packaging, CLI, developer commands, and documentation, with no Node, pnpm, JavaScript, TypeScript, compatibility aliases, or predecessor references outside clearly archived historical evidence.
- [x] **REL-03**: Maintainers can remove the executable compatibility oracle only after Python compatibility, installed-wheel end-to-end, Bundle cross-read, and clean-environment release gates pass, leaving one authoritative implementation and no long-lived dual-runtime matrix.

## Future Requirements

### Extension Ergonomics

- **DX-07**: Publish a supported `openrund.testing` API with reusable store, provider, and Capability contract suites; v2.0 may keep equivalent helpers internal.
- **SYNC-01**: Offer a context-managed synchronous facade that delegates to the async Engine without independent semantics or nested event-loop behavior.
- **PLUG-01**: Offer opt-in allowlisted Python entry-point discovery in the assembly layer; v2.0 uses explicit static registration.

### Scale And Product Expansion

- **SCALE-01**: Add server-grade distributed Event and Artifact storage, fenced multi-host Leases, sharding, and high availability.
- **VIEW-02**: Add persisted View snapshots after replay measurements demonstrate a concrete need.
- **DOC-02**: Add document formats beyond Markdown through separately scoped Capability work.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Hosted multi-tenant control plane | Adds identity, tenancy, service operations, and network Authority beyond the local governed-runtime milestone. |
| Distributed storage, sharding, and HA | Requires a separate consistency and operations milestone after local durability is proven. |
| Rich web UI or workflow builder | Operator presentation and host orchestration must not distract from or become a second legality boundary. |
| Prompt management, planning, personas, or provider routing | These are host/harness concerns rather than governed mutation semantics. |
| Broad first-party Capability catalog | v2.0 preserves the focused filesystem, Markdown documents, process, and local git set. |
| Remote git or credential-bearing network Actions | Expands secrets and irreversible external effects beyond the built-in local coding substrate. |
| Automatic cross-environment resume | Import and ResumeAssessment diagnose local requirements but never grant Authority or bypass explicit rebinding. |
| Permanent API compatibility aliases or dual runtimes | The release is an idiomatic greenfield Python product with compatibility at semantic and serialized boundaries only. |
