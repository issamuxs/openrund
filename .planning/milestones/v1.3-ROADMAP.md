# Roadmap: v1.3 Codebase Map Remediation and Hardening

**Milestone:** v1.3 Codebase Map Remediation and Hardening
**Created:** 2026-05-15
**Source:** `.planning/codebase/`

## Milestone Goal

Implement the actionable corrections from the refreshed codebase map while preserving the mapped architecture, conventions, package boundaries, and test strategy.

## Phases

### Phase 21: Security Boundary Hardening

- [x] Phase 21: Security Boundary Hardening (completed 2026-05-15)

**Goal:** Close the high-priority security gaps identified in the codebase map without weakening the Engine authority model or capability boundary.

**Requirements:** SEC-01, SEC-02, SEC-03, SEC-04

**Success Criteria:**
1. Stdio JSON-RPC worker processes no longer inherit the full parent environment by default.
2. Provider HTTP error surfaces redact sensitive-looking values and avoid leaking request or credential details.
3. Bundle verification rejects unsafe manifest paths before `stat`, `readFile`, or other filesystem access.
4. Filesystem mounts with `posture: "read"` reject all mutating operations inside the capability implementation.
5. Focused tests cover each security boundary and pass with `pnpm test`.

### Phase 22: Durability And Consistency Semantics

- [x] Phase 22: Durability And Consistency Semantics (completed 2026-05-15)

**Goal:** Make persistence-adjacent failure modes explicit, tested, and recoverable where the current local runtime can reasonably support it.

**Requirements:** DUR-01, DUR-02, DUR-03

**Success Criteria:**
1. Event subscriber failure behavior is documented in code semantics and covered by tests for persisted append plus throwing subscriber.
2. Artifact blob/metadata partial failure handling has deterministic cleanup, recovery, or explicit orphan semantics covered by storage tests.
3. Delegation parent/child append partial failures are tested and either repaired, made idempotent, or explicitly reported as recoverable workflow gaps.
4. Changes preserve append-only event ordering and expected-position conflict behavior.

### Phase 23: Source Hygiene And Developer Setup

- [x] Phase 23: Source Hygiene And Developer Setup (completed 2026-05-15)

**Goal:** Remove generated-source drift and make fresh workspace verification less fragile.

**Requirements:** HYG-01, HYG-02, HYG-03

**Success Criteria:**
1. Inappropriate generated `.js`, `.d.ts`, and source map files are removed from source directories.
2. Hygiene checks fail on future generated build artifacts under `packages/*/src`.
3. Python documents worker setup is represented in the root developer flow through documentation or a script.
4. `pnpm hygiene`, `pnpm build`, and the relevant Python worker verification path pass.

### Phase 24: Duplication And Maintainability Reduction

- [x] Phase 24: Duplication And Maintainability Reduction (completed 2026-05-15)

**Goal:** Reduce drift-prone duplicated logic while keeping public exports and runtime authority boundaries stable.

**Requirements:** MAINT-01, MAINT-02, MAINT-03

**Success Criteria:**
1. Provider operation normalization is shared across adapters or enforced by parity tests that make divergence visible.
2. Filesystem implementation duplication is consolidated or covered by explicit parity tests.
3. Any monolith seam extraction is narrow and preserves `RuntimeEngine` as the authority facade.
4. Public API and ontology guard tests continue to pass.

### Phase 25: Performance Pressure Relief

- [x] Phase 25: Performance Pressure Relief (completed 2026-05-15)

**Goal:** Address bounded-output and replay/hash pressure where the codebase map identified scalable local-runtime bottlenecks.

**Requirements:** PERF-01, PERF-02, PERF-03

**Success Criteria:**
1. Process and git capabilities avoid unbounded stdout/stderr memory accumulation for large outputs.
2. A scoped implementation or documented runtime contract exists for reducing repeated full-history view rebuild pressure.
3. Bundle import reuses verified manifest integrity where safe instead of always requiring redundant whole-directory reads.
4. Existing replay, bundle, process, and git tests remain deterministic.

### Phase 26: Verification Closure And Release Readiness

- [x] Phase 26: Verification Closure And Release Readiness (completed 2026-05-15)

**Goal:** Prove the remediation milestone with focused tests, live-provider drift guidance, and full repository verification.

**Requirements:** TEST-01, TEST-02, TEST-03

**Success Criteria:**
1. Every high-priority `CONCERNS.md` remediation has focused Vitest or pytest coverage.
2. Provider live-contract drift has a documented local or CI path that does not require secrets for normal test runs.
3. Tests follow `.planning/codebase/TESTING.md` patterns and avoid mocked runtime authority where real stores/events are appropriate.
4. `pnpm typecheck`, `pnpm test`, `pnpm hygiene`, `pnpm package:check`, and relevant Python tests pass or have explicit documented blockers.
5. Final milestone verification confirms all v1.3 requirements are mapped and either complete or explicitly deferred.
