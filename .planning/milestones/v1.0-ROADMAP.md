# Roadmap: OpenRund

## Overview

OpenRund v1.0 should move from normative specification to a minimal, working runtime that proves the framework's philosophy in practice. The roadmap starts with the canonical execution core, then layers in governed model and capability behavior, including a built-in TypeScript `filesystem` capability and a transported Python `documents` capability with full manipulation support for Markdown-centered workflows, then adds durable waits, bounded delegation, explicit uncertainty, and finally a demo scenario that exercises the full long-running session loop from request to replayable completion.

## Phase Details

### Phase 1: Canonical Runtime Core
**Goal**: Deliver the smallest runtime slice that can create sessions, persist canonical events with strict ordering, rebuild projections, and end sessions lawfully while keeping the semantic core independent from specific capabilities.
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: CORE-01, CORE-02, CORE-03, CORE-04, CORE-05
**Success Criteria** (what must be TRUE):
  1. A new session can be created, started, and terminated with exactly one terminal event.
  2. Event appends are serialized per session with gap-free replay order and stale append rejection.
  3. Working-state and timeline projections can be rebuilt from canonical event history alone.
  4. The runtime core exposes capability dispatch/governance seams without embedding filesystem or document-specific behavior.
**Plans**: 3 plans

Plans:
- [x] 01-01: Define the runtime domain types, event envelopes, and session state machine skeleton.
- [x] 01-02: Implement the event store and append/replay invariants for local execution.
- [x] 01-03: Implement core projections, capability-facing seams, and prove lawful terminal behavior through tests.

### Phase 2: Governed Model And Capability Loop
**Goal**: Let a model request one operation at a time and route accepted capability work through engine validation, canonical action events, policy checks, artifact-backed results, and meaningful first-party `filesystem` plus transported Python `documents` capabilities.
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: MODL-01, MODL-02, MODL-03, CAP-01, CAP-02, CAP-03, AUTH-01, CAP-04, FS-01, FS-02, FS-03, FS-05, DOCS-01, DOCS-02, DOCS-03, DOCS-04, DOCS-06
**Success Criteria** (what must be TRUE):
  1. A model adapter receives only the approved `ModelContext` and emits exactly one runtime operation per step.
  2. Capability actions execute through the full canonical action lifecycle with schema validation and authority checks.
  3. Large action payloads are artifact-backed and observable from event history without bloating events.
  4. A built-in TypeScript `filesystem` capability can perform the core file manipulations agents need within policy-controlled working-directory boundaries.
  5. A Python-backed `documents` capability can read, create, write, and update Markdown files while returning bounded previews plus artifact-backed content and metadata.
  6. Parallel grouped reads are available only for eligible read-only actions and are enforced separately from mutating actions.
  7. The runtime successfully executes at least one transported cross-language capability call to the Python `documents` worker.
**Plans**: 3 plans

Plans:
- [x] 02-01: Define the adapter contract, model step pipeline, and engine-side operation validator.
- [x] 02-02: Implement capability registration, action dispatch, authority hooks, action-group eligibility checks, and canonical action lifecycle events.
- [x] 02-03: Add artifact materialization plus built-in TypeScript `filesystem` and transported Python `documents` capabilities with full Markdown/file manipulation support.

### Phase 3: Durable Waits And Human Control
**Goal**: Support the long-running pause/resume semantics that let sessions wait durably on approval, missing information, and semantic time.
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: FS-04, DOCS-05, WAIT-01, WAIT-02, WAIT-03
**Success Criteria** (what must be TRUE):
  1. A session can pause durably on approval and resume only after a valid approval decision.
  2. A session can request interaction, remain blocked, and continue after the interaction is resolved or cancelled.
  3. Semantic timers can be scheduled, fired, and cancelled without confusing operational backoff with runtime history.
  4. Mutating filesystem and document actions can be blocked on explicit approval before execution.
**Plans**: 3 plans

Plans:
- [ ] 03-01: Implement approval events, waiting state, approval resolution flow, and mutation gating for write actions.
- [ ] 03-02: Implement interaction waits and resume handling for missing information.
- [ ] 03-03: Implement durable semantic timers and their integration with waiting/resumed state.

### Phase 4: Delegation And Context Boundaries
**Goal**: Add bounded child-session delegation and durable compaction so long-running work can split, rejoin, and preserve future context boundaries safely.
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: DELG-01, DELG-02, COMP-01
**Success Criteria** (what must be TRUE):
  1. A parent session can spawn a child session with explicit contract, authority, and handoff input.
  2. A parent can join on child outcomes using explicit join and handoff events rather than inspecting child message history.
  3. The runtime can record compaction boundaries that shape future model context without rewriting canonical history.
**Plans**: 3 plans

Plans:
- [x] 04-01: Implement child-session spawn contracts and lineage tracking.
- [x] 04-02: Implement join semantics, child handoff events, and cancellation coordination.
- [x] 04-03: Implement compaction boundary recording and context-shaping integration points.

### Phase 5: Demo Example And MVP Hardening
**Goal**: Prove the framework with a runnable long-running session example that exercises the full MVP capability set, including document handling, and makes the canonical history easy to inspect.
**Mode:** mvp
**Depends on**: Phase 04.1
**Requirements**: DEMO-01, DEMO-02, DEMO-03, DEMO-04, DEMO-05, DEMO-06, DEMO-07
**Success Criteria** (what must be TRUE):
  1. A demo scenario exercises model output, filesystem manipulation, document creation/editing, artifact creation, waits, delegation, and lawful completion in one end-to-end run.
  2. A developer can inspect the resulting event history and projections to understand what happened without relying on hidden state.
  3. MVP documentation explains how the demo maps back to the normative runtime architecture.
  4. The demo includes an approval-gated write path whose proposed target can be approved as-is or relocated by the approver within declared writable roots, and shows wait/resume behavior clearly in the trace.
  5. The final workspace artifact is validated by a runtime-visible check instead of only assistant claims, while runtime audit exports remain under the runtime home.
  6. The session can be replayed or resumed after interruption while preserving lawful state and outcome.
  7. An ambiguous or interrupted side-effect path demonstrates the Phase 04.1 uncertainty semantics in the trace rather than implementing them locally inside the demo.
  8. Approval resolution can record a policy-constrained approved action revision that preserves action identity, stores the full approved input for replay, may include diff metadata for readable inspection, and is limited by MVP default policy to target/path relocation within declared writable roots.
  9. The runtime can export a portable `.orun` bundle and replay/verify it without depending on hidden local state; cross-environment resume is documented as conditional on rebinding capabilities, policy, providers, waits, and artifacts.
**Plans**: 5 plans

Plans:
- [x] 05-01: Add approved action revision plus typed session contract helpers.
- [x] 05-02: Add validation events, replay projections, and completion blocking.
- [x] 05-03: Add `.orun` portability plus inspection/export CLI commands.
- [x] 05-04: Publish OSS runtime docs and fix `subsession.established` drift.
- [x] 05-05: Implement the canonical research-brief demo with a concrete unknown/reconciled runtime trace.
