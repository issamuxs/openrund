# Plan 21-01: Security Boundary Hardening

## Objective

Implement the Phase 21 security boundary requirements from the codebase map without moving authority out of the Engine or making providers/capabilities authoritative.

## Threat Model

<threat_model>

**Assets protected:**
- Parent process secrets in `process.env`.
- Provider credentials and request details.
- Bundle verifier filesystem boundary.
- Filesystem mount posture and operator-intended read-only roots.

**Threats:**
- High: stdio worker inherits parent secrets and leaks them through worker behavior or crash diagnostics.
- High: provider error bodies echo authorization headers or request payload details into thrown errors.
- High: malicious `.orun` manifest paths cause verifier reads outside the bundle directory.
- High: runtime policy misconfiguration grants a mutating filesystem action against a mount marked read-only.

**Mitigations required:**
- Spawn stdio workers with only `options.env` by default.
- Redact authorization-looking values from provider error details.
- Validate all manifest-declared relative paths before `stat` or `readFile`.
- Enforce read-only mount posture inside `FilesystemCapability` mutating handlers.

</threat_model>

<task id="SEC-01">
<title>Default stdio JSON-RPC worker env to explicit minimal environment</title>

- `packages/capabilities/src/transports/stdio-json-rpc.ts`
- `packages/capability-documents/src/documents-client.ts`
- `tests/capabilities/documents-stdio.test.ts`
</read_first>
<action>
Change `callStdioJsonRpc` so `spawn()` receives `env: options.env ?? {}` instead of `{ ...process.env, ...options.env }`. Keep `cwd`, `args`, and stdio behavior unchanged. Add or update tests so a child process invoked through the transport cannot see a sentinel parent environment variable such as `OPENRUND_SECRET_SHOULD_NOT_LEAK=secret-value` unless that exact key is explicitly provided in `options.env`.
</action>
<acceptance_criteria>
- `packages/capabilities/src/transports/stdio-json-rpc.ts` contains `env: options.env ?? {}`.
- `packages/capabilities/src/transports/stdio-json-rpc.ts` does not contain `...process.env`.
- `tests/capabilities/documents-stdio.test.ts` or a focused transport test asserts a parent-only env var is not inherited.
- `pnpm test -- tests/capabilities/documents-stdio.test.ts` exits 0, or the equivalent focused Vitest command exits 0.
</acceptance_criteria>
</task>

<task id="SEC-02">
<title>Redact provider HTTP error details</title>
<read_first>
- `packages/provider-openai/src/openai-adapter.ts`
- `packages/provider-anthropic/src/anthropic-adapter.ts`
- `packages/provider-local/src/local-openai-compatible-adapter.ts`

- `tests/providers/anthropic.test.ts`
- `tests/providers/local-openai-compatible.test.ts`
</read_first>
<action>
Add a shared local helper pattern in each provider adapter or a small shared helper if cleaner. The error message must keep provider name, status code, and status text, but redact sensitive-looking values from the first 500 response-body characters. Redact bearer tokens, OpenAI-style `sk-...`, GitHub-style `ghp_...`, Anthropic/OpenAI API-key-looking fields, and JSON fields named `authorization`, `api_key`, `apiKey`, `token`, or `password`. Use the exact replacement string `[REDACTED]`.
</action>
<acceptance_criteria>
- Provider adapter errors still include strings like `OpenAI provider request failed (401 Unauthorized)`.
- Provider adapter error tests assert the thrown error does not contain `Bearer secret-token`, `sk-test-secret`, or `ghp_`.
- Provider adapter error tests assert the thrown error contains `[REDACTED]`.
- Focused provider tests for OpenAI, Anthropic, and local adapters exit 0.
</acceptance_criteria>
</task>

<task id="SEC-03">
<title>Reject unsafe bundle manifest paths before filesystem access</title>
<read_first>
- `packages/runtime/src/orun.ts`
- `tests/runtime/orun-bundle.test.ts`
</read_first>
<action>
In `verifyBundle`, validate every manifest-declared path before passing it to `join(input.bundlePath, filePath)`, `statRequired`, or `readFile`. Covered sources include required layout paths, `manifest.exports.runtimeAuditJsonPath`, `manifest.exports.runtimeAuditMarkdownPath`, `manifest.exports.actionReceiptPaths`, `manifest.exports.checkJsonPath`, `manifest.exports.checkMarkdownPath`, and every key in `manifest.integrity.files`. Reject absolute paths, empty paths, paths containing `..` segments, and platform separator escapes such as backslash-separated `..\\secret`. Throw a `BundleRuntimeError` with code `invalid_manifest_path` and the offending `path`.
</action>
<acceptance_criteria>
- `packages/runtime/src/orun.ts` contains `invalid_manifest_path`.
- `verifyBundle` calls path validation before `statRequired` and before integrity `readFile`.
- `tests/runtime/orun-bundle.test.ts` includes traversal/absolute path cases that reject before reading outside the bundle.
- `pnpm test -- tests/runtime/orun-bundle.test.ts` exits 0, or the equivalent focused Vitest command exits 0.
</acceptance_criteria>
</task>

<task id="SEC-04">
<title>Enforce filesystem read-only mount posture inside capability mutations</title>
<read_first>
- `packages/capability-filesystem/src/path-sandbox.ts`
- `packages/capability-filesystem/src/filesystem-capability.ts`
- `tests/capabilities/filesystem.test.ts`
</read_first>
<action>
Add a posture assertion for mutating operations. `write`, `update`, `delete`, and both source and destination sides of `move` must reject when their resolved mount has `posture: "read"`. The rejection must use `capabilityError` with `category: "policy_denied"`, `component: "filesystem_capability"`, and a message that includes `read-only mount`. Leave read/list/stat/diff behavior unchanged.
</action>
<acceptance_criteria>
- `packages/capability-filesystem/src/filesystem-capability.ts` contains `read-only mount`.
- Tests assert `filesystem.write`, `filesystem.update`, `filesystem.delete`, and `filesystem.move` reject against a read-only mount.
- Tests assert `filesystem.move` also rejects when moving into a read-only destination mount.
- `pnpm test -- tests/capabilities/filesystem.test.ts` exits 0, or the equivalent focused Vitest command exits 0.
</acceptance_criteria>
</task>
