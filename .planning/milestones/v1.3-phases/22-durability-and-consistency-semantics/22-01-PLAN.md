# Plan 22-01: Durability And Consistency Semantics

## Objective

Make persistence-adjacent failure modes explicit and tested while preserving append-only event ordering, expected-position conflicts, and Engine-owned authority.

## Threat Model

<threat_model>

**Assets protected:**
- Canonical event log append results.
- Artifact metadata/blob consistency.
- Parent/child delegation history.

**Threats:**
- High: a subscriber throws after event persistence, causing callers to retry an append that already committed.
- Medium: artifact blob write succeeds but metadata write fails, leaving orphan blobs.
- Medium: delegation spawn fails between parent and child appends, leaving parent and child histories inconsistent.

**Mitigations required:**
- Subscriber failures must not reject a committed append.
- New-artifact metadata failures must clean up newly written blobs where possible.
- Delegation partial failure behavior must be covered by tests so future repair work starts from an explicit contract.

</threat_model>

## Tasks

<task id="DUR-01">
<title>Make subscriber failures non-retryable after durable append</title>
<read_first>
- `packages/runtime/src/event-log.ts`
- `tests/runtime/event-streaming.test.ts`
</read_first>
<action>
Change `RuntimeEventLog.publish` so subscriber exceptions are contained after the store append succeeds. The append call must still return `{ appended, nextPosition }` even if one or more subscribers throw. Add a test where a runtime subscriber throws during bootstrap; verify `runtime.bootstrap` resolves, events are persisted, and replay returns the appended events.
</action>
<acceptance_criteria>
- `packages/runtime/src/event-log.ts` catches subscriber failures inside `publish`.
- `tests/runtime/event-streaming.test.ts` includes a throwing-subscriber test.
- The throwing-subscriber test verifies persisted `run.created` and `run.started` events can be read after the subscriber throws.
</acceptance_criteria>
</task>

<task id="DUR-02">
<title>Clean up new artifact blobs when metadata writes fail</title>
<read_first>
- `packages/storage-sqlite/src/sqlite-artifact-store.ts`
- `tests/storage/sqlite-artifact.test.ts`
</read_first>
<action>
Change `SqliteArtifactStore.put` so when a blob is written for a new artifact and the SQLite metadata write fails, the newly written blob is removed before rethrowing the original error. Existing artifact updates may remain best-effort because blob and SQLite cannot be made truly atomic without a larger storage redesign. Add a test that closes the database before `put`, calls `put` with a blob for a new artifact ID, expects rejection, and verifies the blob path does not exist.
</action>
<acceptance_criteria>
- `packages/storage-sqlite/src/sqlite-artifact-store.ts` imports and uses `existsSync` or equivalent to determine whether an artifact row existed before writing.
- `packages/storage-sqlite/src/sqlite-artifact-store.ts` removes a new blob on metadata failure.
- `tests/storage/sqlite-artifact.test.ts` covers metadata failure cleanup for a new artifact.
</acceptance_criteria>
</task>

<task id="DUR-03">
<title>Document delegation partial-failure behavior with an injected failure test</title>
<read_first>
- `packages/runtime/src/runtime-engine.ts`
- `packages/runtime/src/delegation-control.ts`
- `tests/runtime/delegation-spawn.test.ts`
</read_first>
<action>
Add a delegation spawn test with an injected `RunEventStore` wrapper that delegates normal parent appends but throws when appending the child run bootstrap. Verify the parent has the model-call and initial `delegation.created` spawn event, the parent does not have the establishment `delegation.created` event with `parentSpawnEventID`, and the child run has no events. This records the current partial-failure contract explicitly.
</action>
<acceptance_criteria>
- `tests/runtime/delegation-spawn.test.ts` includes an injected child-bootstrap failure test.
- The test verifies parent spawn is durable, parent establishment is absent, and child events are absent.
- Existing delegation spawn tests continue to pass.
</acceptance_criteria>
</task>
