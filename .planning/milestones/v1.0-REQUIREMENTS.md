# Requirements: OpenRund

**Defined:** 2026-05-09
**Core Value:** Provide a minimal but authoritative runtime where long-running agent sessions remain durable, lawful, replayable, and inspectable even when models, workers, or infrastructure fail.

## v1 Requirements

### Runtime Core

- [x] **CORE-01**: Runtime can create a session with explicit initial authority and append immutable canonical events to that session.
- [x] **CORE-02**: Event storage enforces strictly monotonic, gap-free per-session ordering and rejects stale or conflicting appends.
- [x] **CORE-03**: Runtime derives working state and timeline projections by replaying events in canonical position order.
- [x] **CORE-04**: A session can reach exactly one terminal outcome: completed, failed, or cancelled.
- [x] **CORE-05**: The semantic core runtime remains capability-agnostic and does not embed filesystem or document-specific side-effect logic directly.

### Model Boundary

- [x] **MODL-01**: A model adapter receives only the approved five-field `ModelContext` surface.
- [x] **MODL-02**: A model step yields exactly one runtime operation, and the engine validates it before any canonical effect occurs.
- [x] **MODL-03**: Provider and parsing failures are captured in bounded runtime failures without mutating canonical history illegally.

### Capabilities And Authority

- [x] **CAP-01**: Runtime can register governed capabilities with action schemas, reliability metadata, and transport bindings.
- [x] **CAP-02**: A capability action executes through the canonical lifecycle `action.requested -> action.started -> action.completed|failed|cancelled`.
- [x] **CAP-03**: Large capability inputs or outputs are materialized as artifacts and referenced compactly from events.
- [x] **AUTH-01**: Capability bindings and policy rules are represented by explicit authority events and enforced at execution time.
- [x] **CAP-04**: `proposed_action_group` is accepted only for eligible approval-free, non-mutating actions, and the MVP demonstrates grouped parallel reads rather than grouped writes.

### Filesystem Capability

- [x] **FS-01**: The MVP includes a governed `filesystem` capability outside the core runtime rather than embedding file manipulation in engine logic.
- [x] **FS-02**: The `filesystem` capability supports core manipulations needed by agent workflows, including read, write, create, update, move, and delete operations within governed working-directory boundaries.
- [x] **FS-03**: Filesystem capability execution follows the canonical action lifecycle, policy enforcement, artifact discipline, and effect reporting used by other capabilities.
- [x] **FS-04**: Mutating filesystem operations can be policy-gated to require explicit human approval before execution.
- [x] **FS-05**: The default local MVP assembly ships with `filesystem` as a built-in first-party capability implemented in TypeScript.

### Documents Capability

- [x] **DOCS-01**: The MVP includes a `documents` capability outside the core runtime, implemented as a governed capability worker rather than core engine logic.
- [x] **DOCS-02**: The `documents` capability supports Markdown as its initial format and can ingest, inspect, create, write, and update Markdown documents with bounded previews, artifact-backed content, and structured metadata.
- [x] **DOCS-03**: Document capability execution follows the same canonical action lifecycle, policy enforcement, and artifact discipline as any other capability.
- [x] **DOCS-04**: The initial document capability implementation path is Python-based unless a specific document action is better served by another runtime.
- [x] **DOCS-05**: Mutating document operations can be policy-gated to require explicit human approval before execution.
- [x] **DOCS-06**: The MVP demonstrates a real cross-language capability boundary by running `documents` as a Python worker over a minimal transport rather than as in-process runtime code.

### Waits And Human Control

- [x] **WAIT-01**: Runtime can durably pause a session for approval and resume only after a resolved approval event.
- [x] **WAIT-02**: Runtime can durably pause a session for interaction and resume only after missing information or steering is supplied.
- [x] **WAIT-03**: Runtime can durably schedule, fire, and cancel semantic timers as part of session execution.

### Uncertainty And Recovery

- [x] **UNC-01**: Runtime can record an explicit unknown outcome for a started action when the external side effect cannot be safely classified as completed, failed, or cancelled.
- [x] **UNC-02**: Recovery and reconciliation for unknown outcomes are governed by capability reliability class, policy, and evidence rather than hidden automatic retry or rollback.

### Delegation And Context

- [x] **DELG-01**: A parent session can spawn a child session with bounded contract, input, and authority.
- [x] **DELG-02**: A parent session can wait on child joins and consume explicit child handoff events rather than scraping child history.
- [x] **COMP-01**: Runtime can record durable compaction boundaries for future context shaping without rewriting history.

### Demo And Operability

- [x] **DEMO-01**: The MVP includes a runnable demo scenario that exercises model output, filesystem manipulation, document handling, waits, delegation, artifacts, and terminal completion in a long-running session.
- [x] **DEMO-02**: The demo makes runtime history inspectable enough to understand what happened from canonical events and projections.
- [x] **DEMO-03**: The demo includes at least one approval-gated mutating action and visibly shows the proposed write target, approval decision, optional approver relocation within declared writable roots, and resume path.
- [x] **DEMO-04**: The final result is a real workspace artifact written through governed capability approval and validated by a machine-checkable runtime-visible check rather than only model self-report.
- [x] **DEMO-05**: The demo proves recovery by replaying canonical history or resuming after interruption without losing lawful session state or outcome.
- [x] **DEMO-06**: Approval resolution supports a runtime-validated approved action revision that preserves the original action identity while storing the full approved input for replay plus optional diff metadata for inspection readability. MVP default policy permits only target/path relocation within declared writable roots.
- [x] **DEMO-07**: Runtime/library export supports a portable `.orun` session bundle containing canonical events, artifact records/content where available, projection summaries, policy/capability manifests, and integrity metadata; CLI exposes export plus replay/verify for the bundle.

## v2 Requirements

### Platform Growth

- **PLAT-01**: Runtime supports remote or distributed execution leases beyond the initial local assembly.
- **PLAT-02**: Runtime supports richer policy profiles and approval workflows for higher-risk actions.
- **PLAT-03**: Runtime supports a broader catalog of built-in capabilities and example integrations.
- **PLAT-04**: Runtime supports stronger operational tooling for snapshots, migrations, and scale testing.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Multi-tenant hosted control plane | Not needed to validate the core runtime semantics of the MVP |
| Large built-in capability marketplace | Would expand surface area before the engine contract is proven |
| Rich web UI for operations | The MVP should first prove runtime behavior and inspectability through artifacts and projections |
| Distributed scaling and HA orchestration | Adds infrastructure complexity before the minimal runtime loop is stable |
